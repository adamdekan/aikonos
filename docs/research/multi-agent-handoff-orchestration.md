Primary-source research for extending Aikonos with graph-topology subagent orchestration. Every claim below was verified live against official docs, GitHub source, or first-party engineering blogs during this research pass (August 2026). Unreachable/unverifiable sources are called out explicitly rather than filled in from training-data memory.

## 1. LangGraph multi-agent patterns

Sources: the legacy `langchain-ai.github.io/langgraph` doc tree now 301/302-redirects wholesale to the new `docs.langchain.com` platform — every fetch against the old host returned only a redirect stub, so all claims below come from `docs.langchain.com` pages and the `langchain-ai/langgraph*` GitHub source, fetched directly.

- (a) **Control-flow model**: a node or tool returns a [`Command`](https://github.com/langchain-ai/langgraph — `libs/langgraph/langgraph/types.py`) object, a dataclass with fields `graph`, `update`, `resume`, `goto`. `goto` accepts a node name, a `Send` object, or a sequence of either, unifying "what state changes" and "where to go next" in one return value — this replaces separate conditional-edge routing. Verified via direct fetch of the `types.py` source: `graph: str | None = None` (`None` = current graph, `Command.PARENT` = closest parent graph), `goto: Send | Sequence[Send | N] | N = ()`.
- (b) **State/context at handoff boundary**: [handoff tools](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs) return `Command(update={...}, goto=agent_name)`; the `update` dict carries a `ToolMessage` matching the triggering `tool_call_id` (required so the LLM's tool-call/response pairing stays well-formed) plus any state key updates. The docs explicitly warn that only the triggering `AIMessage` + `ToolMessage` should cross a subgraph boundary — passing full history risks "context bloat that could confuse downstream agents." [Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs) either share state keys directly (compiled subgraph added straight to `add_node()`) or, when schemas diverge, a wrapper node function explicitly transforms parent state → subgraph input and subgraph output → parent state.
- (c) **Result aggregation back to parent**: for a shared-schema subgraph, state writes propagate automatically to parent channels. For a schema-mismatched subgraph, the wrapping node function is the sole aggregation point — it receives the subgraph's return value and explicitly returns the mapped update. For handoff-to-parent-graph, `Command(graph=Command.PARENT, goto=...)` routes control (and its `update`) up a level, confirmed in [`langgraph-supervisor-py`'s `handoff.py`](https://github.com/langchain-ai/langgraph-supervisor-py/blob/main/langgraph_supervisor/handoff.py) source (fetched directly): parallel handoffs use `goto=[Send(agent_name, {...}), ...]`, single handoffs use `goto=agent_name` directly.
- (d) **Sandboxing/isolation**: none at the framework level — [subgraph isolation](https://docs.langchain.com/oss/python/langgraph/use-subgraphs) is a *state-schema* boundary (private state keys not visible to the parent) plus a distinct checkpoint namespace per subgraph invocation, not a process/OS isolation mechanism. No sandboxing is mentioned for node execution itself.
- (e) **Authorization/guardrail mechanism**: none documented in the pages fetched. Handoff tools are ordinary LLM-callable tools with no built-in permission gate; any authorization would need to be layered in by the application (e.g., in a custom tool implementation), not something LangGraph provides out of the box.
- **Fan-out/fan-in / map-reduce**: the [`Send` API](https://docs.langchain.com/oss/python/langgraph/use-graph-api) enables *dynamic* fan-out — a conditional edge returns `[Send("node", {...}) for x in items]`, creating one node invocation per item with its own input state (which may differ from the core graph state). Parallel branches from the same node execute concurrently within one LangGraph "superstep," and the superstep as a whole is transactional (all updates succeed or none do). State keys written by multiple parallel branches are merged via per-key **reducers** (e.g., `operator.add` to concatenate lists) — this is LangGraph's aggregator mechanism: no separate "aggregator node" type, the reducer *is* the merge/aggregation step, though a downstream node commonly reads the merged key and does further synthesis.

## 2. OpenAI Agents SDK handoffs vs. tool-calling, and Swarm

Sources: [`openai.github.io/openai-agents-python/handoffs/`](https://openai.github.io/openai-agents-python/handoffs/) and [`.../guardrails/`](https://openai.github.io/openai-agents-python/guardrails/) (fetched directly), and [`openai/swarm`](https://github.com/openai/swarm)'s README (fetched via raw GitHub content).

- (a) **Control-flow model**: a handoff is represented to the model as an ordinary LLM-callable tool (e.g., `transfer_to_refund_agent`), but semantically it transfers *entire* agent control rather than executing-and-returning: "a tool executes and returns to the caller; a handoff passes execution entirely to another agent, which may invoke its own tools and handoffs." Swarm (the predecessor project) implements the same idea more literally at the language level: an `Agent`-returning Python function switches control — "if there is an `Agent` handoff, the `system` prompt will change, but the chat history will not" — driven by `client.run()`'s loop (complete → execute tool calls → switch agent if requested → update context → return).
- (b) **State/context at handoff boundary**: Agents SDK — `input_filter` functions receive `HandoffInputData` (input history, pre-handoff items, new items, run context) and can prune/transform what the next agent sees; an optional `on_handoff` callback fires on invocation and can receive LLM-supplied structured metadata via an `input_type` schema, kept "separate from `RunContextWrapper.context`" (application-level state). Swarm — plain Python `context_variables` dict passed to every agent function and persisted across switches; the richer `Result` object lets one function return a value, a target `agent`, and a `context_variables` update atomically in a single step.
- (c) **Result aggregation back to parent**: for the Agents SDK, results stay within the single active run — the receiving agent's output becomes the run's continuation point (no separate parent/child return; it's a single linear run whose "current agent" pointer changes). Swarm is the same: `client.run()` returns once the (possibly-switched) active agent stops calling tools/handoffs.
- (d) **Sandboxing/isolation**: not addressed by either source at the handoff level — no process or container isolation is described for the handoff mechanism itself.
- (e) **Authorization/guardrail mechanism**: the Agents SDK's [guardrails](https://openai.github.io/openai-agents-python/guardrails/) are input guardrails (run only on the first agent's input, in parallel-by-default or blocking mode) and output guardrails (run only on the final producing agent's output); a triggered tripwire raises `{Input,Output}GuardrailTripwireTriggered` and halts the run. Critically, the docs state explicitly: **"Handoffs run through the SDK's handoff pipeline rather than the normal function-tool pipeline, so tool guardrails do not apply to the handoff call itself."** Guardrails are therefore not an authorization gate on the handoff transition itself — only on the first/last agent's I/O. Swarm has no guardrail or authorization concept in its README.

## 3. Anthropic orchestrator-worker research system, and Claude Agent SDK subagents

Sources: [Anthropic engineering blog, "How we built our multi-agent research system"](https://www.anthropic.com/engineering/multi-agent-research-system) (fetched directly); [`code.claude.com/docs/en/sub-agents`](https://code.claude.com/docs/en/sub-agents) (Claude Code subagents, redirected from `docs.claude.com`, fetched); [`code.claude.com/docs/en/agent-sdk/subagents`](https://code.claude.com/docs/en/agent-sdk/subagents) (Claude Agent SDK, fetched directly, full page content captured).

- (a) **Control-flow model**: a lead agent "develops a strategy, and spawns subagents to explore different aspects simultaneously" — each subagent gets an explicit task spec ("an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"). Typical scaling: simple queries use 1 agent with 3–10 tool calls; complex research spins up 3–5 parallel subagents (10+ for the most complex), each itself able to run 3+ tools in parallel. In the Claude Agent SDK, the equivalent primitive is the `Agent` tool (renamed from `Task` in Claude Code v2.1.63; both names still appear in different surfaces per the SDK docs) invoked with a `subagent_type`; subagents can themselves spawn subagents up to a configurable depth (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, default 3 layers below main).
- (b) **State/context passed at handoff boundary**: per the SDK docs, "the only content you pass from parent to subagent is the Agent tool's prompt string" — a subagent's context window "starts fresh, with no parent conversation." It does receive its own `AgentDefinition.prompt` (system prompt), the Agent-tool invocation prompt, and project `CLAUDE.md` if `settingSources` includes it — but *not* the parent's conversation history, tool results, or system prompt. Tool access is restricted per subagent via the `tools`/`disallowedTools` fields (e.g., a read-only reviewer gets only `Read/Grep/Glob`). The blog's orchestrator-worker description matches this shape at a conceptual level: each subagent "owns its own context window" and the lead agent must externalize its own plan to memory once its context exceeds ~200K tokens (to avoid losing state on truncation).
- (c) **Result aggregation back to parent**: SDK — "only its final message returns to the parent" as the Agent tool's result; the parent may summarize this in its own reply (the docs flag that verbatim preservation needs an explicit instruction). A v2.1.210+ safety scan runs over that final message before the parent reads it, neutralizing control-tag imitation (e.g., a forged `<system-reminder>`), preserving permission-config mentions unmodified, and escaping `Human:`/`Assistant:`-style turn markers — this is a **prompt-injection guardrail on the subagent→parent handoff channel specifically**. The blog describes the equivalent at the conceptual level: subagents act as "intelligent filters," e.g. "returning a list of companies to the lead agent so it can compile a final answer," and the lead agent "synthesizes these results and decides whether more research is needed."
- (d) **Sandboxing/isolation**: the SDK's isolation is a *context-window* isolation (fresh conversation, no inherited history) plus a *tool-permission* isolation (subagents get "a completely isolated tool permission scope that strictly forbids the Task tool" unless explicitly re-granted) — not OS/process sandboxing. No container- or VM-level isolation is mentioned for subagents themselves (that's a separate mechanism, see §5).
- (e) **Authorization/guardrail mechanism**: tool restriction (`tools`/`disallowedTools`, including MCP-server-level wildcard patterns like `mcp__server__*`) is the SDK's per-subagent authorization primitive; `permissionMode` is a further per-agent field. The blog states the system has "explicit guardrails to prevent the agents from spiraling out of control" but does not detail a specific enforcement mechanism beyond scaling rules and task-boundary framing.

## 4. CrewAI hierarchical process, and AutoGen/AG2 GroupChat

Sources: [`docs.crewai.com/concepts/processes`](https://docs.crewai.com/concepts/processes) and [`docs.crewai.com/en/concepts/collaboration`](https://docs.crewai.com/en/concepts/collaboration) (both fetched directly); [`docs.ag2.ai/latest/docs/user-guide/advanced-concepts/groupchat/groupchat/`](https://docs.ag2.ai/latest/docs/user-guide/advanced-concepts/groupchat/groupchat/) (fetched directly).

**CrewAI:**
- (a) **Control-flow model**: the [hierarchical process](https://docs.crewai.com/concepts/processes) requires either `manager_llm` or a custom `manager_agent`. The manager "allocates tasks to agents based on their capabilities, reviews outputs, and assesses task completion" — dynamic delegation, as opposed to the `sequential` process's fixed task order.
- (b) **State/context at handoff boundary**: [collaboration](https://docs.crewai.com/en/concepts/collaboration) is implemented via two auto-granted tools when `allow_delegation=True`: `Delegate work to coworker(task: str, context: str, coworker: str)` and `Ask question to coworker(question: str, context: str, coworker: str)`. The delegating agent must pass "ALL necessary context to execute the task, since they know nothing about the task" — an explicit, manually-authored context string, not automatic history sharing.
- (c) **Result aggregation back to parent**: the manager receives the coworker's tool response synchronously and continues its own reasoning; across sequential tasks, the `context` parameter threads a task's output forward as another task's input ("previous task results become input for dependent tasks").
- (d) **Sandboxing/isolation**: not addressed in either page fetched.
- (e) **Authorization/guardrail mechanism**: `allow_delegation` is the sole gate — `False` on a specialist agent removes both coworker tools outright, which the docs recommend "to prevent re-delegation loops." No finer-grained authorization is documented.

**AutoGen / AG2** — note on the project split, confirmed directly from the primary source ([`microsoft/autogen` GitHub Discussion #7066](https://github.com/microsoft/autogen/discussions/7066), posted by AutoGen maintainer Eric Zhu, fetched via `gh api`): *"AutoGen and Semantic Kernel are merging into a single, unified framework under the name Microsoft Agent Framework... AutoGen will still be maintained — it has a stable API and will continue to receive critical bug fixes and security patches — but we will not be adding significant new features to it."* Full detail also on [Microsoft's own devblog](https://devblogs.microsoft.com/agent-framework/migrate-your-semantic-kernel-and-autogen-projects-to-microsoft-agent-framework-release-candidate/). Separately, a community fork under new stewardship (`ag2ai`) continues independent development of the pre-merge AutoGen 0.2-style API/architecture as **AG2** — this document cites AG2's docs (`docs.ag2.ai`) since it is the actively-developed continuation of the exact GroupChat/DiGraph API researched here; the pre-fork docs also still exist at `microsoft.github.io/autogen/0.2/` describing the same API.

- (a) **Control-flow model**: a `GroupChatManager` agent orchestrates the loop — it selects the next speaker, that agent responds, the manager broadcasts the message to every other agent in the group, and repeats up to `max_round`. Four `speaker_selection_method` options: `auto` (LLM-driven using agent descriptions, the default), `round_robin`, `random`, `manual` (human-directed).
- (b) **State/context at handoff boundary**: "All agents contribute to a single conversation thread and share the same context" — every agent sees the full accumulated `messages` list; there is no per-agent context filtering by default (contrast with LangGraph's deliberate context-bloat avoidance at handoff, §1b).
- (c) **Result aggregation back to parent**: results aggregate implicitly through the shared message list — the manager collects each speaker's output and broadcasts it as input context to the next selected speaker; an `is_termination_msg` condition can end the round loop early. There is no distinct "aggregator" step separate from the broadcast mechanism itself.
- (d) **Sandboxing/isolation**: not documented on this page.
- (e) **Authorization/guardrail mechanism**: none documented — agent descriptions and system messages are *behavioral* steering, not access control. The one structural constraint is the **DiGraph-based speaker-transition constraint**: `allowed_or_disallowed_speaker_transitions` is a dict mapping an agent to a permitted (or forbidden) list of next-speakers, with `speaker_transitions_type` selecting which sense applies — e.g. `number_agent → [adder_agent, number_agent]`. This constrains *which agent may run next*, functioning as a structural (not permission-based) guardrail on control flow, useful as agent count grows since "the number of transition pairs increases exponentially."

Supplementary architecture detail (e2b, from the same `ARCHITECTURE.md`): sandboxes start from pre-booted VM snapshots (memory+disk+state in object storage) rather than cold boot; memory is lazy-loaded via `userfaultfd` page-fault handling against the template's memory file, and storage uses copy-on-write overlays over a read-only template rootfs — this is what gets claimed startup times down near-instant rather than a full kernel boot per sandbox.

## 6. Reference architectures: map-reduce, fan-out/fan-in, blackboard

- **LangGraph's `Send` API** (§1) is itself a documented map-reduce primitive: dynamic fan-out to N node instances with per-instance input state, reducer-based merge back into shared state keys — [`docs.langchain.com/oss/python/langgraph/use-graph-api`](https://docs.langchain.com/oss/python/langgraph/use-graph-api).
- **Anthropic's orchestrator-worker pattern** (§3) is a fan-out/fan-in architecture in substance even though the blog never uses "map-reduce": lead agent fans out 3–10+ parallel subagents with disjoint task boundaries, each returns condensed findings, lead agent performs the reduce/synthesis step — [anthropic.com/engineering/multi-agent-research-system](https://www.anthropic.com/engineering/multi-agent-research-system).
- **AWS Prescriptive Guidance**, [Multi-agent collaboration](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-patterns/multi-agent-collaboration.html) (fetched directly): explicitly distinguishes centrally-coordinated "workflow agents" from decentralized "multi-agent collaboration," and its implementation-guidance table names **"shared memory"** (Amazon DynamoDB / S3 / OpenSearch) with the purpose "**Multi-agent memory or blackboard system**" — this is the one primary source found that names the blackboard pattern explicitly, alongside a separate orchestration-layer row (AWS Step Functions / Lambda pipelines) for "Kickoff, timeout, fallback, and retry logic."
- **Google's ADK developer blog**, [Developer's guide to multi-agent patterns in ADK](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/) (fetched directly): documents a `ParallelAgent` primitive for fan-out — sub-agents run concurrently and must each write to a unique session-state key to avoid races — followed by a sequential "gather" agent that reads the merged keys, then an explicit synthesizer/aggregator agent (example: a `PRSummarizer` consolidating Security/Style/Performance sub-agent findings into one review). This is the clearest primary-source example of a distinct, named aggregator step (as opposed to LangGraph's implicit reducer-based merge).

## Synthesis (original reasoning, not cited research)

Three architecture options for extending Aikonos with graph-topology subagent orchestration plus an aggregator node. Design reasoning only — no code, no schema changes proposed.

### Option A — `kind: "subagent"` step, still inside the linear workflow engine

**Control-flow model (Aikonos terms):** extend `Step.Kind` with a third value, `"subagent"`, alongside the existing `"tool"`/`"reason"`. A subagent step names a bound agent (or an inline persona) and a sub-prompt; `run.ts`'s step driver spawns it, waits for completion, and stores its condensed output as `StepOutcome.output`, exactly like a `"reason"` step but backed by a full agent turn (its own tool calls) instead of one bounded LLM call. `${steps.N.output}` cross-refs keep working unmodified.

**Mapping onto existing primitives:**
- Natural extension of the workflow `Step` system — same per-kind `validate()` in `broker/internal/workflow/workflow.go`, same `ComputeRequires` skip-rule precedent already used for `"reason"` steps.
- `ChildSupervisor` spawns a **new forked child process** per subagent step, keyed like any other user/agent session (per-user or per-agent keying, matching the existing pool). This is the natural extension: Aikonos's child-per-session model already is the isolation primitive Claude Agent SDK's "fresh context window" gives for free — Aikonos gets it as a side effect of already forking a process per session.
- Biscuit tokens: each subagent's tool calls go through the **ordinary** `SubmitPlan → OPA → FGA → Biscuit → InvokeTool` path, scoped to that step exactly as any workflow tool step is today — no new token type needed, no inherited authority from the parent workflow run. The subagent step itself is not privileged; it just happens to drive a nested agent loop instead of one tool call.
- The workflow remains **linear at the top level** — a subagent step is a single node in the existing sequence, not a graph. This stays entirely inside `workflow.go`/`run.ts`; the cron scheduler is unaffected/orthogonal (a subagent-bearing workflow schedules exactly like any other).

**Net-new vs. reuse:** net-new is limited to the step kind + driver branch + child-spawn wiring for that step. No graph executor, no new broker task states, no new infra service.

**Open questions/risks:**
- Per-subagent re-validation is literally "just extend per-step re-validation to one more step kind" — no new invariant needed, this is the cleanest inheritance of the existing zero-inherited-authority model.
- A parent workflow that spawns N subagent steps sequentially still pays N full child-spawn costs; fine for occasional use, poor fit if the real ask is *parallel* fan-out (see Option B).
- Failure handling is trivial here because it's linear: a failed subagent step halts the workflow exactly like a failed tool step does today (existing `failedSteps` tracking in `run.ts`) — no partial/parallel-branch semantics to design.

### Option B — graph executor with `kind: "parallel"` fan-out + a dedicated `"aggregator"` step

**Control-flow model:** introduce a graph-shaped alternative to the linear `Step` sequence — a workflow can declare a DAG of steps where some steps are marked to run concurrently (`kind: "parallel"`, a set of branch step-lists) and one designated `kind: "aggregator"` step consumes all branch outputs (`${branches.*.output}`) once every branch in its dependency set completes.

**Mapping onto existing primitives:**
- This is **not** a natural extension of `run.ts`'s current single-cursor step driver — that driver assumes one active step advancing linearly. A DAG needs an actual **graph executor component**: tracking a frontier of ready steps, dispatching concurrently, joining at aggregator nodes. This is net-new infrastructure, structurally analogous to (but simpler than) LangGraph's `Send`+reducer model researched in §1 — Aikonos would need its own minimal join/reducer concept, since Go/TS here has no LangGraph dependency to borrow.
- Each parallel branch that itself contains a `kind: "subagent"` step (Option A) spawns its own forked child via `ChildSupervisor`, so branches run as genuinely concurrent child processes — this is where fan-out actually gets wall-clock parallelism, not just logical parallelism.
- Aggregator step: a new step kind, bounded like `"reason"` (a single parent-side LLM call with a fixed instruction template), but with a different input contract — it receives the full set of upstream branch outputs rather than one prior step's output. No broker gate/execute call needed for the aggregation itself (same "no authority" precedent as `"reason"`), but each branch's own tool calls inside the fan-out are still independently re-validated.
- New broker task states are probably *not* needed if the whole graph run is still modeled as one `tasks` row with the graph execution happening gateway-side (mirroring how a linear workflow run today is one gateway-orchestrated sequence, not N broker tasks) — but this needs confirming against how `CreateGatewayTask`'s per-step Biscuit minting currently assumes one step in flight per task; a graph with true concurrent branches may need N concurrent step-tokens open against the same task simultaneously, which is a broker-side assumption to verify before committing to this design.
- Cron scheduler stays orthogonal here too — a graph workflow is schedulable the same way a linear one is; the graph executor is a run-time concern, not a scheduling concern.

**Net-new vs. reuse:** the graph executor itself, the branch-join/aggregator dispatch logic, and (likely) a review of the broker's per-task step-token assumption are all net-new. The per-step OPA/FGA/Biscuit re-validation, the `"reason"`-step-style bounded aggregator call, and `ChildSupervisor`'s per-session spawn are all reused as-is.

**Open questions/risks:**
- **Partial/parallel-branch failure**: needs an explicit policy, not an implicit one. Two reasonable defaults: (1) *fail-fast* — one branch's tool-call denial or exec failure aborts the whole graph run (matches today's linear-workflow "halt on first failure" behavior, easiest to reason about, easiest to audit); (2) *degrade* — the aggregator step runs anyway over whichever branches succeeded, with failed branches represented as an explicit "failed" marker in their slot (mirrors the AWS-guidance and Google-ADK model of a synthesizer that tolerates partial input) — riskier because it means an aggregator step (a bounded LLM call with no broker gate) is the thing deciding how much a partial failure matters, and that call has no independent authority check of its own. Recommend fail-fast as the default policy and treat "degrade gracefully" as an explicit per-workflow opt-in the workflow author must declare, not silent default behavior.
- Concurrent Biscuit-token issuance per task (multiple branches executing simultaneously against one nominal task) is a broker-side assumption that has not been verified in this research pass and should be checked against `service_invoke.go`/`gateway_tasks.go` before design commitment.

### Option C — sandboxed coding subagent as a dedicated microservice (office-worker precedent)

**Control-flow model:** a `kind: "subagent"` (or a specialization of it, e.g. `agent_role: "coder"`) step whose execution is *not* another forked Pi child but a call out to a new stateless microVM/container sandbox service — architecturally the same shape as the existing `office-worker` service (§5's e2b/Anthropic-code-exec research directly informs this): no long-lived credentials in the sandbox, ephemeral per-invocation container, request/response over an internal-only network, output artifacts staged back through the existing `workspacefs`/toolproxy save-to path rather than a new file channel.

**Mapping onto existing primitives:**
- This is explicitly **not** a natural extension of `ChildSupervisor` — the whole point of a coding subagent is untrusted code execution, which is a different threat model than "another LLM turn in a forked Node process." `ChildSupervisor`'s existing invariant (no long-lived secrets in the forked child, parent proxies provider calls) already assumes the child is *trusted but sandboxed against secrets*; a code-exec sandbox needs to be *sandboxed against the host and network too* (per §5, Firecracker/container isolation, no internet access, workspace-scoped file access only) — a strictly stronger and different isolation requirement.
- Net-new infrastructure: a dedicated sandbox microservice (mirrors `office-worker`'s existing precedent of "dedicated no-egress, no-credential service, stateless multipart in/out" almost exactly) plus a new toolproxy-style plugin exposing it as a gated tool/step.
- The step that *invokes* the sandbox still goes through ordinary `SubmitPlan → OPA/FGA → Biscuit → InvokeTool` — the sandbox call is just another gated tool call from the broker's point of view, with no new authority model needed there. The isolation strength is a property of the sandbox microservice, not of the broker's authorization path.

**Net-new vs. reuse:** net-new is the sandbox microservice itself (the actual infrastructure lift) plus its toolproxy plugin registration. Reused: the gate/execute path, workspacefs staging for artifacts (same pattern office-docs tools already use for save_to/from_path), and the office-worker precedent for hardening (`no-new-privileges`, `cap_drop ALL`, `read_only`, non-root, mem_limit) that Aikonos's compose stack already applies to every new service.

**Open questions/risks:**
- Timeout/resource-limit policy has to be decided explicitly per §5's comparison — Aikonos doesn't need Firecracker-grade multi-tenant isolation if the sandbox is single-purpose and ephemeral per call (closer to Anthropic's/OpenAI's container model), but does need *some* hard wall-clock and memory cap mirroring those two, since an agent-authored coding step is the least-trusted content this system runs.
- This option composes with Option A or B (the sandbox is just what a `"subagent"` step's `agent_role: "coder"` variant calls into) rather than replacing either — it's an addition to the execution backend of a subagent step, not a fourth standalone architecture.
- Partial-failure semantics for a sandbox call are simpler than Option B's graph case: a sandbox timeout/crash is just a failed tool-step, same `failedSteps`-halts-workflow behavior already in `run.ts` — no new failure-handling design needed here specifically, only in whichever of Option A/B provides the enclosing control flow.

### Cross-cutting notes

- All three options preserve Aikonos's standing invariant — **no blanket inherited authority** — because none of them proposes a token that widens scope across a handoff; every option keeps re-validation at the same granularity Aikonos already uses per tool-call/per-step, just extended one level (per-subagent, per-branch, or per-sandbox-call).
- The cron scheduler is unrelated to all three: whichever shape wins, a graph/subagent-bearing workflow is scheduled exactly like today's linear ones — the scheduler ticker only cares about firing a workflow lineage, not about what's inside it.
- Option A is the cheapest to ship and should probably land first regardless of longer-term ambition, since Option B's graph executor and Option C's sandbox microservice both benefit from having a working "one subagent step" primitive to build on top of.
